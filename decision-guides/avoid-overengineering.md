# Avoid Overengineering

完整不等于复杂。一个软件应该识别所有模块，但不一定第一天实现所有模块的企业级版本。

## Start Simple When

| 条件 | 简化选择 |
| --- | --- |
| 只有一个开发者 | 单体应用 |
| 用户量未知 | 托管平台 + PostgreSQL |
| 没有复杂权限 | 简单 RBAC |
| 没有复杂搜索 | 数据库查询先行 |
| 文件很少 | 托管对象存储 |
| 没有团队协作 | 先不做组织/租户 |
| 没有真实支付 | 先做订单状态模拟 |

## Add Complexity When

| 信号 | 增加能力 |
| --- | --- |
| 权限规则开始混乱 | 引入权限模型和矩阵 |
| 查询变慢或搜索体验差 | 引入搜索服务 |
| 任务耗时影响请求 | 引入队列 |
| 文件变多或变大 | 完善对象存储和处理 |
| 付费用户增加 | 完善账单、发票、客服 |
| 事故定位困难 | 完善监控、日志、追踪 |
| 团队协作变多 | 完善文档、CI/CD、测试 |

## Senior Rule

每新增一个复杂组件，都应该能回答：

```text
它解决了哪个已经出现的问题？
如果不用它，最坏会怎样？
谁维护它？
怎么测试它？
怎么部署和恢复它？
```

回答不出来，就先不要加。
